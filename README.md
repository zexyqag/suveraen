# suveraen

Free and open-source services for a small community, self-hosted: files and documents, photos, chat, passwords and more, federated where that applies. Everything is public, including the configuration of the servers it runs on, so all of it can be scrutinized.

It runs on Kubernetes (k3s) over NixOS, built to start on one server and grow to several with failover. A small separate watcher machine keeps an eye on it from outside.

**Status:** the server layer is in place, and so is the frame for the cluster's own services: the gateway, certificates, storage, databases, accounts and the template every app follows. The first app, a mesh between people's devices, is in place too (below); the others come next.

## Layout

- `nixos/`: the server layer, NixOS modules configured under `suveraen.*`.
  - `storage.nix`: one disk or two mirrored (ZFS) for the system and the cluster's own state, encrypted unless the machine must reboot unattended. Encrypted ones boot through [lanzaboote](https://github.com/nix-community/lanzaboote) under Secure Boot with their own keys, and only from their own system disks: each opens only as the volume it was installed with, by its key's id, which `suveraen-volume-key-ids` prints from the volume's header and the passphrase, as disko does at install, and the root pool is imported from those alone. A mirror comes up degraded on one disk when the other is missing or holds another volume, which the hourly health check reports, and a volume the passphrase doesn't open keeps the boot asking until its disk is taken out. Container images and pods' scratch space are bounded, etcd and Ceph's monitors reserved space. The other disks are Ceph's, each under a stable name with a logical volume for its OSD's database on the system disks, mirrored over both, so losing either costs no OSD. Hourly snapshots, scrubs, health checks, and on a server, an alert before the pool or a bounded dataset fills; logs, the servers' metrics and what their checks keep, and the watcher's cache of alerts and Gatus's results lie on datasets of their own outside the snapshots, so they last no longer than they are kept.
  - `unlock.nix`: on encrypted machines, an SSH server during boot that takes the disk passphrase, also from keys that may do nothing else. Its host key is sealed to the machine's TPM, so only the machine's own signed boot chain, under its own Secure Boot keys and with nothing loaded from the boot partition, can answer, and the system that chain boots, which can too, is the machine's own. Root on the running server can still take the key, and so can whoever gets the TPM's secrets out of it, and an earlier copy of its disks put back boots as the server did when it was taken, as does a copy of either disk of a mirror once the other doesn't open. `suveraen-unlock-seal` makes the key on the machine; until then the server answers with a transition key and every boot alerts. Before the passphrase it shows the TPM's boot count, which the server posts once unlocked, alerting when boots in between never unlocked, a TPM restart could hide one, or the firmware changed. After each boot and upgrade, a check alerts when the next boot couldn't open the key or couldn't undo a firmware reset from the boot menu.
  - `network.nix`: static or DHCP IPv4, static IPv6.
  - `resolver.nix`: every machine resolves names itself with [Unbound](https://nlnetlabs.nl/projects/unbound/) (DNSSEC, no outside resolver), and so do the cluster's pods.
  - `time.nix`: clocks follow several independent time servers over NTS, which authenticates their replies; a server's metrics read from chrony itself whether it is synchronised, and alert when it has had no source for six hours, or the clock is a second off.
  - `cluster.nix`: a k3s server with embedded etcd, snapshotted every 6 hours and compressed, secrets encrypted at rest (secretbox), a cluster token read from a file, without which a snapshot can't be restored, and one command that restores one with it (`suveraen-etcd-restore`), WireGuard between nodes, dual-stack networking, and k3s's own images loaded from its release's tarball, which nixpkgs pins by hash, rather than pulled by tag. It installs [Flux](https://fluxcd.io), which keeps the cluster in sync with this repository and installs only the charts it ships, its pods held to network policies of the server's own, to which the release adds none: they reach one another, the cluster's DNS and the API server, and source-controller also the repository's port anywhere but the cluster's pods and Services and link-local addresses (the nodes' own addresses stay in, as the release's settings hold the cluster's nodes and a server knows only its own), and nothing but one another and the node itself reaches them; rights within a namespace don't extend to Flux, pods must meet the restricted Pod Security Standard (except in `rook-ceph`, where Ceph's daemons and CSI plugin run privileged, the node plugin on the host's network, so it reaches whatever the host does, which no network policy holds and the host's firewall lets out unfiltered), Services can't take external IPs, on the host pods reach only the API server, the kubelet, the resolver and, on the DNS signer, its Knot, and the platform's pods run ahead of tenants'; a shutdown stops tenants' pods first and Ceph's last, once every volume is unmapped. With `stun.port` set, its addresses answer STUN on that UDP port (coturn, STUN alone, no client's address logged), so that devices behind NAT can connect to each other directly. Its firewall counts how fast each address, an IPv6 one by its /64, opens web connections and sends STUN requests, in memory alone, drops those past a rate and keeps out for a while what `suveraen-block` names. Its metrics come from the kubelet, read with an account that may read its metrics and nothing else, from etcd, and from the runtime's records of containers and systemd's journal of those the kernel killed for memory: they alert when a container keeps restarting or the kernel kills one for memory, a volume or etcd fills, or a tenant takes much of the node's CPU or stalls on I/O, of which only sums per namespace are kept.
  - `mirror.nix`: every image the cluster pulls comes through the server's own mirror ([Zot](https://zotregistry.dev), built from source with nothing but its sync), which fetches each from its registry the first time containerd asks for it and keeps it, also once the registry has deleted it, on a bounded dataset of its own outside the snapshots. containerd pulls from nowhere else, so an image from a registry the mirror doesn't list (`suveraen.mirror.upstreams`, which always holds Docker Hub, GitHub's, Quay and Kubernetes' own) isn't pulled at all. The mirror answers on loopback alone, to root alone, and takes no push or delete. A server alerts when an image it holds isn't wholly in its mirror, when the mirror stops answering and when pulls keep failing; `suveraen-mirror fill` fetches again what is missing or damaged.
  - `dns.nix`: authoritative DNS with [Knot](https://www.knot-dns.cz). A hidden server signs the zones (DNSSEC, one key per zone that never changes by itself) and is the only one that takes changes: certificate challenges, in a zone of their own, from cert-manager's key alone, which a restart of `knot-acme-key` replaces. Published secondaries, ours and a provider's, follow it. Zones get CAA records, and a null MX, SPF and DMARC unless they send mail. The keys are backed up after boot and daily by default, encrypted, and the backups go off-site with the server's own state where it has providers for it (`offsite.nix`), as a cluster's servers do; on a signer in the cluster their age, and their copies', is checked with the other backups', and a secondary or a new signer takes them over from that backup, also while knot won't start without them.
  - `dns-check.nix`: the watcher checks every 15 minutes that all nameservers serve the same signed zones, that the signatures are being renewed, and that each parent delegates with the NS and DS records declared for the zone; problems reach ntfy through Gatus.
  - `watcher.nix`: the watcher. [ntfy](https://ntfy.sh) for alerts (only known accounts, instant on Android and iPhone, no account API or attachments) and [Gatus](https://gatus.io), which checks the public services and raises an alert when a server stops reporting in, and while an encrypted one waits for its disk passphrase.
  - `alerts.nix`: failed jobs and disk or RAID problems are posted to the watcher's ntfy on a secret topic, with a second channel for when the watcher can't be reached; servers report in to Gatus every few minutes, and say there when their checks have stopped or alerts get nowhere, which a publish tries once a day, and on the second channel when the watcher's ntfy stops answering.
  - `source.nix`: the repository and branch a machine and its cluster follow, and the release signers: with signers set, Nix on the machine and Flux in the cluster refuse a branch head that none of them signed.
  - `upgrade.nix`: machines switch to their configuration from that branch nightly. Unencrypted ones reboot by themselves when needed; encrypted ones send an alert instead. A machine also alerts when the configuration it runs gets old, or while new ones keep coming, when the nixpkgs they lock does.
  - `host-checks.nix`: every 15 minutes each server checks, from status alone and with an account that may read little else, how old each tenant's WAL archiving, base backups, off-site copies, checks and volume copies are against what their templates allow, how old its own etcd snapshots and DNS key backups, and their off-site copies, are, and Ceph's health; whether Flux's objects are ready, none stays suspended, and Flux applies the release the server runs; whether cert-manager issues and renews every certificate in time; whether each of the gateway's edges answers it through the gateway; whether its own addresses answer STUN; what the rules on its own metrics find (`metrics.nix`); and as root, with no credential, whether each tenant's Kanidm keeps its admin accounts disabled and applied its migrations, whether each app's copy of its client's secret is right, and whether each tenant's mesh keeps to the operator's rules: no exit, nothing exposed, no rule for everyone, shares one way on named ports, every device in its own person's group and every box in one home's, one owner, no tokens or powers over devices, its settings, the oldest release it takes, no one still in whom Kanidm let go, no device's inventory kept, and the server's STUN port as the cluster names it; and whether each tenant's vault keeps an account open, enabled or with a device's session, for anyone Kanidm let go or linked to none of its people (`vault.nix`); it alerts once when that changes, daily while it lasts, and when the cluster, the rules, or a tenant's Kanidm, mesh or vault, can't be checked, and notes each change of who can reach what in a mesh once.
  - `metrics.nix`: each server keeps its own metrics ([VictoriaMetrics](https://victoriametrics.com)), scraped only from itself and only what a rule reads, on loopback behind a password that never leaves it, for 14 days, dropped a month at a time so up to about 45, on a dataset of its own outside the snapshots and never backed up. [vmalert](https://docs.victoriametrics.com/victoriametrics/vmalert/) evaluates the rules each module declares on them and sends nothing, its own among them, on units that fail without alerting by themselves or keep restarting, memory running low or stalling and a filling connection table, and keeps of some only sums by the labels a job names; what no target gives, modules measure with scripts it runs as root on a read-only system, and with such scripts they make what the store reads a target with, such as a token, which only it may read; the servers' checks read what they find (`suveraen-metrics check`), alert on it, keep what can't be told while a target or an input is lost, and alert when the rules can't be checked.
  - `idm.nix`: `suveraen-idm`, each tenant's Kanidm from a server, by exec into its pod with an account it recovers for the run alone, after which idm_admin, admin and anonymous are disabled again, and at its public name through the server's own gateway, never looked up in DNS: `admin` makes a new person a platform or tenant admin, who gets a link to enrol passkeys, a platform admin's to open only at the server's own gateway, and sets Kanidm's own groups, so that tenant admins make their tenant's people, reset the credentials of those who are no admins and change the members of its groups; `sync` copies each confidential client's secret from Kanidm into its app's Secret where that is wrong and applies the clients' flags, to run after a release adds such a client, after `suveraen-etcd-restore` and after a cluster is rebuilt; `rotate` gives a client a new secret, and `rotate --all` every client, after Kanidm's volume is restored; `accounts` tells how Kanidm answers for people by their IDs, for the mesh's check.
  - `mesh.nix`: `suveraen-mesh`, each tenant's mesh from a server, by exec into the tenant's PostgreSQL as the mesh's own role: `check` reads what the servers' checks judge in a session that starts read-only, as `sql` runs a query of the operator's; once a restore has taken the tenant's PostgreSQL back, `after-restore` raises its mesh's network serial past every one its devices hold and starts its management again, so that running devices take the restored mesh rather than ignore it.
  - `vault.nix`: `suveraen-vault`, each tenant's vault from a server, its accounts read by exec into the tenant's PostgreSQL as the vault's own role, in a session that starts read-only: `check` reads what the servers' checks judge, and `users` lists a tenant's accounts by their IDs and their Kanidm people's, with no mail or name; `offboard` ends every way into the account of a person Kanidm let go, never of one it still lets in, nor while it is enabled of one linked to none of its people, by a second Vaultwarden that serves the admin pages on the vault pod's loopback alone for the run, under a token of its own that no command line holds: it asks the relay to forget their phones, and names those it may still know when that failed, ends their devices' sessions and disables the account, its API key and its Sends with it; `erase` does that, then deletes the account with its vault and files; each prints the account's ID for the deletion record, by which a run after a restore finds it once Kanidm has let its person go again; `relink` links the account of a person Kanidm lost to the one it made again for them.
  - `offsite.nix`: each server given providers, as a cluster's must be, copies its own state, its etcd snapshots and on the DNS signer its key backups, to both, encrypted with [age](https://age-encryption.org) to recovery keys that no server holds, a key backup over its own encryption. One unit without network encrypts, another uploads with a key that reaches only that server's own prefix and deletes nothing, and the bucket's lock keeps every copy for as long as it lasts.
- `kubernetes/`: what Flux applies, from the release branch.
  - `clusters/<name>/`: one directory per cluster, which a server's `suveraen.cluster.path` names. It lists the platform and the cluster's tenants, and holds its settings (including whether it is a test cluster, whose tenants are stand-ins), its secrets (the accounts at both CAs, encrypted on every cluster but a test one), its hostname map, which gives each name to a tenant or one of its app namespaces, and the names its DNS answers inside the cluster, each tenant's identity host with its Kanidm (encrypted on every cluster but a test one, like the map); `test` is the one CI deploys.
    - `tenants/<id>/`: one tenant, under a random five-character ID: Kustomization and Secret `tenant-<id>` (its domains and keys, encrypted on every cluster but a test one) and the list of app templates it runs. The members are a tenant like any organisation.
  - `platform/`: the gateway (Gateway API on [Traefik](https://traefik.io) on every node, which gets each client's own address, limits its requests and gives apps a pseudonym per host in its place, under a key held only in memory for a set period such as a day), certificates ([cert-manager](https://cert-manager.io)) from a public ACME CA with a second one on standby, over DNS-01 through the node's own nameserver, restarts on changed settings ([Reloader](https://github.com/stakater/Reloader)), storage on [Ceph](https://ceph.io) run by [Rook](https://rook.io) (encrypted disks, three copies of everything, placement groups that follow its OSD count, byte quotas on the pools that hold data, block volumes with snapshots that go with their claims and an object store in the cluster that serves S3 and Rook's admin API alone; its namespace is the one privileged exception), copies of apps' volumes ([VolSync](https://volsync.readthedocs.io)), the charts apps are built from, and the policies every tenant and app is held to, among them that every pod outside `kube-system` runs only images named by digest, and that every egress rule of a network policy names what it reaches (Rook's install keeps only the ingress of the CSI operator's chart's own, whose one egress rule reached everything, and the policy the operator makes for each driver's controller plugin, whose rule does too, is refused, which every pass it makes over the driver reports).
  - `components/`: what a tenant's apps get: its own namespace per app, closed by default but for web ports anywhere outside the cluster for the platform's backup jobs and an app's proxy alone (`internet`, the one way to the internet, which a platform piece's namespace can take too), and held to a quota, whose charts can act only there (`app`) and, like the platform's, are tried again every two minutes when an install or upgrade fails, until it succeeds, never rolled back or uninstalled (`retry`); the tenant's label on all of it, and the tenant's own settings but never the cluster's secrets (`tenant`); an app's own database and role in its tenant's PostgreSQL, reached from its namespace alone (`db`, `db-client`); for an app that calls hosts on the internet, a proxy in its namespace that tunnels HTTPS to the hosts its template lists and refuses every other, whose list its charts can't change (`egress`); a volume copied to both providers with restic, encrypted with the app's own password, which the app's charts can't delete, and made anew from the latest restore from either provider, with a daily check at each provider that reads every copy back once a week, without restic's lock (`volsync`); for an app that terminates TLS itself, its own certificate for its one host (`passthrough`, or `passthrough-app` for a host on the tenant's app domain); an app's groups and OAuth2 client in its tenant's Kanidm, the way there from its namespace, and for a confidential client the Secret its secret is copied into from Kanidm, never through the repository (`sso`, `sso-client`, `sso-secret`); for an app that reaches the cluster's hosts at their public names, the roots the public issuer's certificates chain to beyond those images hold, none on a real cluster (`public-roots`).
  - `edge/`: one host of a tenant's app: a Gateway with a single listener for that name and its certificate, in the gateway namespace where no app reaches, and the route to the app. The host is on the tenant's app domain (`app`), on its own domain (`identity`), or that domain itself (`apex`). A host on its own domain may instead be passed through, still encrypted, to an app that terminates TLS itself (`passthrough`), which the gateway limits only by new connections, and so may one on its app domain (`passthrough-app`).
  - `apps/`: one directory per app. `ks.yaml` is the template a tenant lists: the app, the hosts every tenant gets and its database, if it has one; `edge-<key>.yaml` adds a host a tenant may choose. `postgres` is the tenant's own PostgreSQL ([CloudNativePG](https://cloudnative-pg.io)), one cluster for all its apps, which archives its WAL and base backups to the tenant's bucket in the cluster, copies its running generation to two providers encrypted with the tenant's own key, where a daily check at each, reading only, finds every copy whole and reads each back once a week, and is restored as a new generation of itself, from the cluster's bucket or a provider's copy. `kanidm` is the tenant's accounts ([Kanidm](https://kanidm.com)), at `idm.` on its own domain, which terminates its users' TLS itself; its groups and every app's OAuth2 client are Kanidm's own migration files: one that makes each entry once and never changes, one for the platform and each app that states what it sets on them and applies again as it changes, and one that removes those it no longer has. No admin account holds a standing credential. Every ID those files declare, but the founding groups', comes from the tenant's own encrypted Secret, so no one in the tenant knows one before Kanidm makes its entry. `netbird` is the tenant's mesh ([NetBird](https://netbird.io)) at `netbird.` on its app domain, passed through to its own nginx, which routes the mesh's five paths alone: members sign in with the tenant's Kanidm, and its state is in the tenant's PostgreSQL, where a trigger keeps what devices report beyond the mesh's needs, their serial numbers and interfaces' addresses and MACs, out of every row, so out of the WAL and backups too. `vaultwarden` is the tenant's passwords ([Vaultwarden](https://github.com/dani-garcia/vaultwarden)) at `vault.` on its app domain, behind the gateway, whose accounts the tenant's Kanidm alone makes, for Bitwarden's own apps to sign in to; its vaults are in the tenant's PostgreSQL, their attachments and Sends on its volume, and phones get its notifications through Bitwarden's relay, in the EU unless the tenant names another, which its proxy (`egress`) alone reaches.
- `release/approve.sh`: `approve` shows what changed on `staging` since the last release, and once you confirm, signs it and publishes it to `main`. It refuses a candidate in which a file that makes a Kanidm entry holds other text than `main` first held under its ID or for that entry, as Kanidm would then fail that file at every start, and for a repository on GitHub it refuses until every check on the candidate has passed. ## Mesh

A tenant that lists `apps/netbird/ks.yaml` gets a private network between its people's devices: [NetBird](https://netbird.io), WireGuard from device to device, at `netbird.` on the tenant's app domain, its state in the tenant's PostgreSQL and backed up with it. Devices connect directly where they can, finding their way with the servers' STUN, so two that do learn each other's public address; otherwise they go through the mesh's relay.

Each person's devices reach each other, what that person chooses at home and what others share with them, and nothing else: NetBird's rule that lets every device reach every other is never made, and a person's devices are in a group of their own. A box at home that stays on joins with a one-off key instead of a sign-in, into that person's home group: it is reached only on the ports its person names and reaches nothing itself, and the same goes for what it routes to at home that can't run NetBird, a camera say. Sharing one of them with someone else is one rule, one way, to that one host on named ports. These are rules for the mesh's owner, the first person to sign in to it, who sets them up in NetBird's dashboard, which shows everyone else nothing. NetBird can't be told to refuse what they forbid, so the servers' checks read how the mesh is set up every 15 minutes, alert on what breaks them (`host-checks.nix` above says what they look for), and note each change of who can reach what, a person's new device among them.

What doesn't rest on the owner: the mesh's pods reach nothing but the cluster's DNS and the tenant's Kanidm and PostgreSQL, so the servers are no way out to the internet for a device (a box at home could be made one, which the checks alert on); the mesh's own nginx answers its paths alone, so NetBird's setup, invitations and reverse proxy can't be reached; it sends no metrics, looks up no location, keeps no activity log, and the names it would call home at resolve to its own pod, while its dashboard's pages may reach nothing but the mesh and the tenant's Kanidm. NetBird knows a person by their Kanidm ID alone, never their name or e-mail, and the address it records a device connecting from is its own nginx's.

People sign in at the tenant's own Kanidm, as members of its group `netbird-users`, which tenant admins manage, and the owner approves a person before their first device gets in; their later devices need no approval. Each device's sign-in asks Kanidm to have the person sign in again, and Kanidm's pages ask them to, but at Kanidm 1.11.2 to 1.12.1 a browser already signed in to Kanidm as the person can skip that step: such a browser is enough to add a device as them, so people keep their Kanidm sign-in off browsers others use. Members of `netbird-users` can enrol only passkeys, but Kanidm applies that only as a credential is enrolled, never at sign-in: a password a person held before they joined keeps working, for the mesh and every other app, until they next change their credentials. So a person joins the group before they enrol any, and one who already has a password gets a reset at once, where saving a passkey removes it; nothing checks for a password left over. What guards a device's sign-in is therefore the person's Kanidm session, the credential they hold and the mesh's login expiry, which the checks hold to 7 days at most (`suveraen.checks.mesh.loginExpiry`), after which each device signs in again. Leaving the group takes no device off the mesh before then; blocking the person in NetBird does at once, and the checks alert while someone Kanidm let go isn't blocked.

People install NetBird's own app on their phones, tablets and computers and set its server to `https://netbird.<app domain>` before they first sign in, as it otherwise signs in to NetBird's own service. On computers, NetBird's app also asks cloud providers' metadata addresses about the machine at each start, which no setting stops; its apps for phones and tablets don't. A device has to run a release no older than the floor the servers' checks name (0.78.0 by default, `suveraen.checks.mesh.minimumClient`): every rule asks it of the device a connection starts from, and since a device reports its release itself, the checks alert on any below it. CI runs NetBird's Linux client at the servers' release and at that floor; its other apps run in no test here.

## Passwords

A tenant that lists `apps/vaultwarden/ks.yaml` gets a password manager for its members: [Vaultwarden](https://github.com/dani-garcia/vaultwarden), which Bitwarden's own apps and browser extensions sign in to, at `https://vault.<app domain>`. Each person's vault is encrypted on their devices under a master password that the server never sees, so it can't check its length: Bitwarden's apps ask for at least 20 characters as it is first set. Vaults are kept in the tenant's PostgreSQL; attachments and Sends, up to 100 MiB of each a person, and the key Vaultwarden signs its sessions with are on its volume. Accounts are made through the tenant's Kanidm alone, by any member with a mail address: their first sign-in makes their account and links it to their Kanidm ID, never to their mail, which names the vault from then on, whatever Kanidm later holds. There is no sign-up form, no invitation and no admin page but the one `suveraen-vault` serves on the vault pod's loopback for a run, and Vaultwarden takes its settings from its release alone. A device signs in through Kanidm, or by the account's API key, which its person gets with their master password and Kanidm never sees. Vaultwarden keeps its own sessions, renewed as they are used, for 30 days and 90 on phones, so Kanidm can end none of them: a person Kanidm lets go keeps every device signed in, and with the API key signs in new ones, until `suveraen-vault offboard` ends that, which the servers' checks alert on while it waits. Leaving the vault takes being expired or deleted in Kanidm: a person only taken out of the tenant's `members` group can't sign in through Kanidm again, but keeps their devices and API key, and the checks don't see them. Phones with Bitwarden's apps get notice of a change at once through Bitwarden's relay, in the EU unless the tenant names another, which the vault reaches through its own proxy alone, as the tenant's own installation there, whose ID and key are in the tenant's Secret: the relay, and the services behind it that reach the phones, learn the IDs of an account, its devices and what changed, and when, never a mail address, a name or what a vault holds. The relay's hosts serve Bitwarden's own cloud too, and the proxy sees only their names, so it holds the vault to them, not to the relay alone. Emergency access and organisations stay off until the platform sends mail, without which a recovery would reach its grantor unannounced and a person would join an organisation without being asked; icons are never fetched, by the vault or from elsewhere, and Duo, HaveIBeenPwned and Yubico never asked, which render holds its settings to, and password hints never kept.

## Releases

Changes land on `staging`, which the watcher runs first. The servers and the cluster only deploy `main`, and `main` only moves through releases signed with a key listed in `release/signers`. A server also refuses a release older than the one it runs.

To release, work in a clone of the repository with git's `user.signingkey` set to your SSH signing key (a security key works). The very first time, run `nix run .#approve -- --first-release`. After each release, approve prints the command for the next one: it runs approve from the last signed release, whose signature Nix checks first, so your working tree never decides what gets signed.

Each release can carry a warrant canary: approve shows its statements and signs them into the release's commit message only if you type `true`. Anyone can read it on `main` and check its signature against `release/signers`. If the newest release has no canary, one of its statements may no longer hold.

## Use

Add the flake as an input and import `nixosModules.default`:

```nix
{
  inputs.suveraen.url = "github:<owner>/suveraen";

  outputs = { suveraen, ... }: {
    nixosConfigurations.myhost = suveraen.inputs.nixpkgs.lib.nixosSystem {
      modules = [
        suveraen.nixosModules.default
        ./myhost.nix
      ];
    };
  };
}
```

`checks/server.nix`, `checks/watcher.nix` and `checks/ns.nix` show every setting each kind of machine needs.
